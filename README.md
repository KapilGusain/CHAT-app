#  Realtime Chat Application

A scalable, realtime chat application built with **Next.js, Socket.IO, PostgreSQL, Prisma, Redis/Valkey, and Auth.js**.

The application provides a modern messaging experience with realtime communication, persistent messages, online/offline presence, read receipts, image sharing, message editing, deletion, search, pagination, and conversation management.

---

##  Features

###  Authentication

* Secure authentication using **Auth.js**
* JWT-based sessions
* Protected API routes
* Authenticated Socket.IO connections
* Conversation membership validation

###  Messaging

* Realtime one-to-one messaging
* Persistent messages using PostgreSQL
* Message timestamps
* Message editing
* Delete message for both users
* Message search
* Paginated message loading
* Deterministic conversation handling

###  Image Messaging

* Send images inside conversations
* Image uploads using **Supabase Storage**
* Image metadata persisted in PostgreSQL
* Stores:

  * Image URL
  * File name
  * File size
  * MIME type

###  Read Receipts

* Message delivery/read status
* Single tick for delivered messages
* Double tick for read messages
* Conversation-level read state
* Unread message counts
* Read receipts persisted in the database

###  Presence

* Realtime online/offline status
* User-specific Socket.IO rooms
* Presence synchronization across connected clients

###  Realtime Architecture

* Socket.IO for realtime communication
* Separate realtime server
* Redis/Valkey adapter for scalable Socket.IO communication
* User rooms
* Conversation rooms
* Realtime conversation updates
* Realtime unread-count updates

###  Conversation Management

* Direct conversations
* Duplicate direct-conversation prevention
* Conversation membership checks
* Conversation list updates
* Message history loading
* Unread count management

##  Project Structure

The project is split into the web application and the realtime server.

The realtime server does not blindly trust a client connection. A realtime authentication token is generated by the application and verified by the Socket.IO server.

---

#  Socket.IO Rooms

The application uses two main room types.

### User Room

```text
user:{userId}
```

Used for user-specific realtime events such as:

* Online/offline presence
* Conversation updates
* Unread-count updates

### Conversation Room

```text
conversation:{conversationId}
```

Used for:

* New messages
* Message updates
* Message deletion
* Conversation-specific realtime events

This room structure allows the realtime server to target events efficiently rather than broadcasting everything to every connected client.

---

#  Database

The application uses **PostgreSQL** with **Prisma ORM**.

Important data models include concepts such as:

```text
User
 │
 ├── Conversations
 └── Messages

Conversation
 │
 ├── ConversationMember
 └── Message

Message
 │
 ├── MessageRead
 └── Image Metadata
```

Messages can contain normal text or image information.

Image-related fields include:

```text
imageUrl
imageName
imageSize
imageMimeType
```

---

The actual image file is stored in Supabase Storage while the message database stores the information required to display and identify it.

---

#  Read Receipts

Read state is tracked using conversation-level and message-level information.

```text
Message sent
     │
     ▼
Delivered
     │
     ▼
Receiver opens conversation
     │
     ▼
Read state updated
     │
     ▼
Sender receives realtime update
     │
     ▼
✓✓
```

The application uses `ConversationMember.lastReadAt` along with message read records to manage read state and unread counts.

---

#  Online / Offline Presence

Presence is managed through Socket.IO connections.

```text
User connects
     │
     ▼
Socket authenticated
     │
     ▼
User marked online
     │
     ▼
Presence event
     │
     ▼
Other relevant users updated

User disconnects
     │
     ▼
Presence updated
     │
     ▼
User marked offline
```

Redis/Valkey helps coordinate realtime state when multiple realtime server instances are running.

---

#  Scalability

The application separates the web application from the realtime server.

```text
                 ┌─────────────┐
                 │   Browser   │
                 └──────┬──────┘
                        │
             ┌──────────┴──────────┐
             ▼                     ▼
       Next.js Server       Socket.IO Server
             │                     │
             │                     ▼
             │               Redis / Valkey
             │                     │
             ▼                     ▼
        PostgreSQL          Other Socket Servers
```

Using the Redis/Valkey adapter allows Socket.IO events to propagate between multiple realtime server instances.

This makes the architecture suitable for scaling beyond a single realtime server.

#  Installation

## 1. Clone the Repository

```bash
git clone <your-repository-url>

cd CHAT-app
```

---

## 2. Install Web Dependencies

```bash
cd web
npm install
```

---

## 3. Install Realtime Server Dependencies

```bash
cd ../realtime
npm install
```

---

## 4. Configure Environment Variables

Create the required `.env` files and configure:

* PostgreSQL
* Auth.js
* Redis/Valkey
* Supabase
* Socket.IO
* Realtime authentication secrets

---

## 5. Configure Prisma

From the `web` directory:

```bash
npx prisma generate
```

Run database migrations:

```bash
npx prisma migrate dev
```

---

## 6. Start the Next.js Application

From:

```bash
cd web
```

Run:

```bash
npm run dev
```

The web application will normally run at:

```text
http://localhost:3000
```

---

## 7. Start the Realtime Server

From:

```bash
cd realtime
```

Run the realtime server using your configured development command, for example:

```bash
npm run dev
```

The Socket.IO server is configured to run separately from the Next.js application.

#  Security Considerations

The application includes several security layers:

* Authenticated user sessions
* JWT-based realtime authentication
* Conversation membership validation
* Protected API routes
* Server-side database operations
* Environment-based secrets
* User-specific Socket.IO rooms
* Conversation-specific Socket.IO rooms

Clients should never be trusted to determine whether they are members of a conversation. Membership must be validated server-side before accessing or modifying conversation data.
